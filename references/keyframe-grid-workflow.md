# 关键画面引导工作流 · keyframe-grid-v1

本流程用于明确选择九宫格的任务或已有 keyframe-grid-v1 项目；新完整项目默认见 [空间预演参考流程](spatial-reference-workflow.md)。

## 创作和确认

1. 先理解情节，给出中文导演稿，确认拍法、表演、台词语气与视频任务划分。正文沿用场景、镜头运动、人物运动顺序。为每个生成任务分配时长，H3单任务4–15秒；导演组可包含多段并超过15秒。
2. 先确认人物基准，再生成四张独立视图及每人一张原尺寸合图，执行 character-reference.md。已有合格的同版本人物图直接复用；无人物任务登记说明，不为填阶段虚构人物或生图。
3. 每个视频任务生成一张3×3九宫格。每一格都是目标视频里的完整关键画面，包含场景、人物位置、动作姿态、构图和光影。生成时实际引用人物图，不能只在文字中提到参考文件。不要把白模、纯背景人物图、平面图混作其中的格子。逐格校对人物一致性、动作衔接、物件状态、空间和光线，再让用户确认。图像工具使用当前环境能力；不能用文字或Python图形冒充真实生成的画面。
4. 围绕已确认图片写目标提示词及完整中文对照。人物合图提供身份；九宫格提供画面与顺序。提示词交代格间运动、切镜、时长、对白与声音。H3读取 h3-official-skill.md 与 h3-handoff.md，用Ref2VA独立编译，不经旧review同步关卡。缺失图片、编译失败或未核实的槽位不得标为正式交付。
5. 确认后交付每段所需人物合图、九宫格、原始画面（如有）、提示词和中文对照、真实文件到槽位的映射。人物可以共用，但每个任务的最终输入与文本自足。不要把九宫格直接放首帧槽，否则整张拼图可能成为开场画面。

九宫格不是九个镜头，也不按每格一秒机械分配。连续镜头可用多格表达关键状态；不同镜头之间明确切点。每段维护 panel-map.json：task_id、duration、九格各自的panel编号(1–9)、time_seconds、shot_id、完整画面描述、与下一格的连接方式（continuous/cut/hold），以及人物素材版本。时间按剧情分配、顺序递增或明确停留；切镜时间对应提示词。它是内部交付说明，不是H3专有控制语法。九格不能因填表增加无意义事件，平静段落可展示同一动作的渐变与停留。

场景需跨段一致时，复用已确认的场景依据或前段完整画面；只有确有需要才另外建立场景／道具基准。简单情节不要求平面图和白模。需要空间验证时在九宫格定稿前完成相关辅助检查，人物可使用明确标注用途的简化占位体，精确表演才需要成熟绑定。

## H3 描述原则

按实际槽位在subject_definitions定义人物Subject及九宫格Picture。九宫格说明从左到右、从上到下编号，并明确它映射哪些Shot及关键时刻；各格是完整剧情画面，不是九个人同时出现。retention_analysis只保留所指定的内容、构图和关键状态，不保留网格、边框、编号。detailed_description按真实播放过程写；要求正常单画面视频，格间是自然动作或指定切镜，不是静态幻灯片。不能只写“按图生成”。这些是本项目基于官方分镜参考机制的使用约定，不是官方九宫格专用语法或硬锁帧功能。

人物四视图的纯白背景不能带进剧情九宫格。人物图与九宫格冲突时先修图，不能只靠文字宣称消除矛盾。每个人物合图和每段九宫格各占一个图片槽位，按最终实际输入核验9图及混合总量限制。生成九宫格可整图生成后检查，或生成独立关键画面后无缩放排版；保存真实输入与版本。具体尺寸按工具能力选择，不保证生成工具能提供请求的任意分辨率，也不保证H3预处理不缩图。

## 独立进度与页面

此版本以轻量文件记录实现新模式，不改旧review/state.json，也不自动迁移旧项目。使用已有虚拟环境：

```sh
.venv/bin/python scripts/grid_workflow.py init /新项目目录
.venv/bin/python scripts/grid_workflow.py register /新项目目录 --stage director --files director.md
.venv/bin/python scripts/grid_workflow.py confirm /新项目目录 --stage director --evidence '实际用户确认原话'
.venv/bin/python scripts/grid_workflow.py status /新项目目录
```

阶段依次为director、characters、grids、prompts。register以项目相对路径登记实际文件（同阶段全部文件），不生成内容；confirm只记录真实用户批准。每次登记都撤销该阶段和下游旧批准；status计算当前文件哈希，文件变动会令本阶段过期并阻止下游沿用确认。修改后必须重新登记；即使内容改回，重新登记也不会复用旧批准。重复确认同一有效版本不撤销下游。登记与确认保存前一版阶段记录供追溯（不复制图片内容，原图仍应另存版本）。这是旧整体登记模式的规则。新完整项目可按人物和任务逐项登记，局部依赖和交付清单见 [交付与复用](grid-delivery.md)；已有整体记录不自动转换。

人物阶段登记四张原图与合图、来源记录；grids登记所有任务九宫格及panel-map；prompts登记编译结果、中文对照和素材映射。没有适用人物时登记一份明确的无人物说明，批准仍由用户提供，不伪造图片。status 只核对进度。grid validate 另检查材料、panel-map 的九格编号、时间和镜号、人物版本及槽位；九格视觉内容、图像质量、语义和用户身份仍由助手实际检查，不能把 status 或 validate 当导演质量证明。

每次操作保留静态index.html摘要。交互审阅启动 `scripts/grid_workflow.py serve PROJECT --port 0`，使用输出的完整带token回环URL打开同一审核页；不能直接双击静态index.html来进行编辑。助手每次交付都打开或刷新该URL并给出链接。旧项目继续使用原review-serve，不自动迁移。

交互页展示四阶段、原图与合图、九宫格、文本及中文对照；可编辑已登记的.md/.txt中文导演稿、提交各阶段修改意见、点击确认当前版本。目标提示词与JSON是只读材料，修改意图通过导演稿或意见交给助手同步，不允许直接改英文却留着旧中文。页面按钮确认是真实用户依据，助手测试只能对测试项目操作。

页面每3秒检查成果；没有未保存输入时自动展示更新，有草稿时提醒而不覆盖，手动刷新保留草稿供合并。旧revision不能写入或确认新成果。未保存输入会阻止确认，离开页面有提醒。提交修改意见后阶段进入待修改并撤销下游确认，助手处理并重新登记前不能批准。CLI与HTTP写入共用项目文件锁；网页不会自动生图或调用H3，用户保存／确认后回当前对话继续。

新流程最终交付使用专门的目录与清单，不调用要求旧布局关卡的validate --strict / groups-package冒充新模式验收；独立h3.py校验及文件、槽位人工核对仍必做。按 [交付协议](grid-delivery.md) 使用 grid validate / package，可输出通用 ZIP 和 AIMixer 原生格式包，无需补做白模。格式校验通过不等于目标导入或视频生成效果已验证。
